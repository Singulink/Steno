# Steno and General Compressors

**A general compressor and the Steno Encoding (Steno for short) are tools for different jobs, and they combine.** On values of up to 16 characters every compressor measured is larger than Steno, and larger than plain UTF-8; on paragraphs and whole documents the strongest are smaller than Steno, by up to 60% over a group of values. Choose Steno for the values and keys that a store compares and sorts, and a compressor for long documents that are stored and read back whole, or on top of Steno for whole pages.

The compressors measured are Deflate, Brotli, LZ4 and Zstandard (Zstd), each at a fast and a strong level, each on the UTF-8 of each value by itself, with nothing shared between values.

## Why Choose Steno for Stored Values

- **Smaller short values.** On 16-character UDHR values every compressor is larger than Steno (1.11 bytes per character) and than UTF-8 (1.92): the smallest of them, Deflate at its strongest level, takes 1.96. A compressed value carries its own overhead, and a short value has no repetition to find.
- **Bytes a store can work on.** A compressed value keeps none of the order, the prefixes or one encoding per text, so a store must decompress it to compare it and cannot range-scan or prefix-match it; and equal text has equal bytes only as long as the compressor, its version and its level stay the same.
- **Speed.** The .NET reference implementation encodes far faster than the compressors at their strong levels ([Speed, Head to Head](#speed-head-to-head)).

## Where a Compressor Is the Better Choice

- **Far smaller on long text.** A compressor finds repetition across a whole text, which a per-value encoding cannot. Over whole UDHR documents Brotli at level 11 takes 0.42 bytes per character, against 1.05 for Steno.
- **It works on any bytes.** A compressor is not limited to text.

## Properties

| | UTF-8 with a general compressor | Steno |
|---|---|---|
| Bytes sort in code point order (the order of the characters' Unicode numbers) | No | Yes |
| Prefix of the text, prefix of the bytes | No | Yes |
| One encoding per text | No: another compressor version or level can give other bytes | Yes |
| No 00 byte | No | Yes, U+0000 included |
| Line feed, tab, carriage return and space bytes never part of another character | No: a compressed value can contain any byte value | Yes: 03 is always a line feed, 02 a tab, 05 a carriage return and 07 a space ([§13.5](../reference/specification.md#135-no-byte-below-08-inside-a-code-point)) |
| Standard | Each compressed format has its own specification | Steno Encoding, version 1, an open specification, free to implement |
| Implementations | Many libraries | Reference implementations in C, .NET, Go, Java, Python, Rust and TypeScript |

## Both Together

The two combine. A store can keep each value in Steno, so that it can compare and sort the values as bytes, and still compress whole pages or blocks of values when it writes them to disk, where the compressor finds repetition across many values. That combination was not measured here.

## Choosing

- **Choose Steno when** a store keeps values and keys that it compares, sorts or matches as bytes, and compress the pages or blocks on top of it if long-text size matters too.
- **Choose a general compressor when** long documents are stored and read back whole, and never compared, sorted or searched as bytes.
