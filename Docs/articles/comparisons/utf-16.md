# Steno or UTF-16?

**The Steno Encoding (Steno for short) is smaller than UTF-16 over every group of values measured, and in 555 of the 565 sets of values (one language or text at one length of value); for alphabets it is about half the size.** UTF-16 needs no transcoding where strings are UTF-16 in memory, and it is smaller on very short Chinese and Korean values, by up to 10%. Choose Steno for stored text and keys; UTF-16 suits text that stays in the memory of a .NET, Java or JavaScript program.

## Why Choose Steno over UTF-16

- **About half the size for alphabets.** UTF-16 is 58% to 92% larger than Steno over each group of values: on 16-character values it is 98% larger in Latin script, 83% in Cyrillic and 86% in the Indic scripts.
- **Smaller on Japanese and Korean past the first few characters.** On 16-character values UTF-16 is 26% larger than Steno in Japanese and 10% larger in Korean. In Chinese the two are close: UTF-16 is 9% larger on Wikipedia values and 0.6% smaller on UDHR values.
- **Bytes that sort like the text.** UTF-16 code units do not sort in code point order (the order of the characters' Unicode numbers) where a supplementary character, such as an emoji, meets U+E000..U+FFFF; Steno bytes always do.
- **No 00 byte.** UTF-16 bytes are full of 00 bytes (every ASCII character has one), so they cannot be ended with 00 inside a composite key.
- **Line feeds and tabs that can be found in the bytes.** In Steno the byte 03 is always a line feed and 02 always a tab, so encoded text can be split into lines and fields without decoding it, and Steno values can be kept one per line or in tab-separated data. In UTF-16 these byte values can be part of other characters.

## Where UTF-16 Is the Better Choice

- **No transcoding in some languages.** .NET, Java and JavaScript keep strings as UTF-16, so storing UTF-16 is a copy.
- **A fixed size for most text.** Every character below U+10000 takes 2 bytes, whatever the script.
- **Smaller on very short Chinese and Korean values.** On 4-character values UTF-16 is 9% smaller than Steno in Chinese and 5% smaller in Korean, and up to 10% smaller in a single language. The first ideograph or syllable of a value takes 3 bytes in Steno, which weighs most on the shortest values.

## Properties

| | UTF-16 | Steno |
|---|---|---|
| Bytes sort in code point order (the order of the characters' Unicode numbers) | Not with emoji and other supplementary characters | Yes |
| Prefix of the text, prefix of the bytes | Yes | Yes |
| One encoding per text | Yes, for one byte order | Yes |
| No 00 byte | No | Yes, U+0000 included |
| Line feed, tab, carriage return and space bytes never part of another character | No: each character is two or four bytes, and any byte value can be one of them; U+0A0D, for example, contains the byte 0A | Yes: 03 is always a line feed, 02 a tab, 05 a carriage return and 07 a space ([§13.5](../reference/specification.md#135-no-byte-below-08-inside-a-code-point)) |
| Standard | Unicode standard | Steno Encoding, version 1, an open specification, free to implement |
| Implementations | Every platform | Reference implementations in .NET, Rust, C, Go, Java, TypeScript and Python |

## What It Means for a Store

These follow from the measured sizes; none of them was measured in a database. The speed of UTF-16 was not measured.

- **About twice the values per page for alphabets (calculated).** On 16-character values, 544 Latin values fit in 8 KB in Steno against 275 in UTF-16, and 507 Cyrillic values against 277. In Chinese the two are tied (332 against 334).
- **Less to read and to cache, smaller index keys**, in proportion to the sizes above.
- **Order on the bytes.** An index on UTF-16 bytes is out of code point order wherever supplementary characters occur; an index on Steno bytes is not.

## Choosing

- **Choose Steno when** a store keeps the text and compares or sorts it as bytes.
- **Choose UTF-16 when** text stays in the memory of a program whose strings are UTF-16, or when the values are only a few Chinese or Korean characters (UTF-16 is up to 10% smaller on 4-character Chinese values) and no store compares them as bytes.
