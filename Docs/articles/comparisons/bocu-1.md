# Steno or BOCU-1?

**BOCU-1 is the closest alternative: like the Steno Encoding (Steno for short), it keeps the order of the text. Steno is 1% to 12% smaller over every group of values measured, and smaller in 506 of the 565 sets of values (one language or text at one length of value).** BOCU-1 is smaller on very short values in six scripts above U+0EFF, by up to 17% at 4 characters. Choose Steno for stored values and keys in many languages; choose BOCU-1 where a system already reads it, or where most values are very short text in those six scripts.

## Why Choose Steno over BOCU-1

- **Smaller overall.** BOCU-1 is 1% to 12% larger than Steno over each group of values. On 16-character values it is 35% larger in Japanese, 28% in Armenian, 18% in Vietnamese, 9% in Latin script and 8% in Chinese.
- **No 00 byte at all.** BOCU-1 writes U+0000 as the byte 00; Steno never writes 00, so 00 can end any field of a composite key.
- **Speed, text by text.** [Speed, Head to Head](#speed-head-to-head) compares Steno with ICU's BOCU-1 in native code, on each text of the shared workloads. ICU is called once per value; another BOCU-1 implementation may be faster or slower.

## Where BOCU-1 Is the Better Choice

- **Smaller on very short values in six scripts.** In Georgian, Khmer, Burmese, Tibetan, Amharic and polytonic Greek, BOCU-1 is 6% to 17% smaller than Steno on 4-character values and up to 6% smaller on 16-character values. The first letter of these scripts takes 3 bytes in Steno, once per value.
- **Each line decodes on its own.** BOCU-1 resets its state at every C0 control character, line feed, carriage return and tab included (UTN #6 §2.4), so each line of a BOCU-1 text can be decoded without the lines before it. Steno finds the lines of a text in its bytes, but decodes a line only with the text before it; an application gets the same as BOCU-1 by encoding each line as a value of its own.

## Properties

| | BOCU-1 | Steno |
|---|---|---|
| Bytes sort in code point order (the order of the characters' Unicode numbers) | Yes (UTN #6 §2.2) | Yes |
| Prefix of the text, prefix of the bytes | Yes in every check on the benchmark corpus (ICU's converter); UTN #6 does not state it | Yes |
| One encoding per text | Yes: every encoder gives the same bytes (UTN #6 §2.4) | Yes |
| No 00 byte | Except for U+0000 | Yes, U+0000 included |
| Line feed, tab, carriage return and space bytes never part of another character | Yes: like 00, 07, 08, 0B, 0C, 0E, 0F, 1A and 1B, these bytes are never trail bytes (UTN #6 §2.3, and the trail byte table of the sample code, which §5 makes the full specification); the other control bytes can be | Yes: 03 is always a line feed, 02 a tab, 05 a carriage return and 07 a space ([§13.5](../reference/specification.md#135-no-byte-below-08-inside-a-code-point)) |
| Specification | Unicode Technical Note #6 | Steno Encoding, version 1, an open specification, free to implement |
| Implementations | ICU | Reference implementations in C, .NET, Go, Java, Python, Rust and TypeScript |

## What It Means for a Store

These follow from the measured sizes; none of them was measured in a database.

- **More values per page in most scripts (calculated).** On 16-character values, 544 Latin values fit in 8 KB in Steno against 500 in BOCU-1, 518 Armenian values against 404, and 387 Japanese values against 287. In Khmer and Burmese BOCU-1 fits about 6% more.
- **Less to read and to cache, smaller index keys**, in proportion to the sizes above. Both keep the order, so both work as index keys on the bytes.

## Choosing

- **Choose Steno when** a store keeps text values and keys in many languages and works on them as bytes.
- **Choose BOCU-1 when** a system already reads BOCU-1, or when most values are very short text in Georgian, Khmer, Burmese, Tibetan, Amharic or polytonic Greek.
