# Steno or UTF-8?

**For stored values, the Steno Encoding (Steno for short) is smaller than UTF-8 over every group of values measured, and in 545 of the 565 sets of values (one language or text at one length of value); UTF-8 is smaller in none. Both keep the order, the prefixes and one encoding per text.** UTF-8 transcodes faster and every system reads it. Choose Steno for the text values and keys that a store keeps and compares; choose UTF-8 for text that you exchange with other systems.

## Why Choose Steno over UTF-8

- **Smaller values outside ASCII.** UTF-8 is 38% to 81% larger than Steno over each group of values. On 16-character values UTF-8 is 70% larger in Cyrillic, 73% in Greek, 155% in the Indic scripts, 174% in Thai and Lao, 88% in Japanese, 47% in Chinese and 37% in Korean. In Latin script the two are close: 1.01 against 1.06 bytes per character, and English is 1.00 in both.
- **The same work on fewer bytes.** Compare, sort, range-scan, prefix-match and hash work on Steno bytes as they do on UTF-8 bytes, so a store does the same work on fewer bytes.
- **No 00 byte at all.** UTF-8 writes U+0000 as the byte 00; Steno never writes 00, so 00 can end any field of a composite key.

## Where UTF-8 Is the Better Choice

- **It transcodes faster.** UTF-8 needs no state: for a system that already holds UTF-8, storing it is a validated copy, which no encoding step can beat ([Speed, Head to Head](#speed-head-to-head)). Steno's state is what makes its bytes small, and a store that works on the bytes pays the transcoding only when text enters or leaves it.
- **It is universal.** Every system, language and protocol reads UTF-8. Steno is read by its reference implementations and by anyone who implements the [specification](../reference/specification.md).

## Properties

| | UTF-8 | Steno |
|---|---|---|
| Bytes sort in code point order (the order of the characters' Unicode numbers) | Yes | Yes |
| Prefix of the text, prefix of the bytes | Yes | Yes |
| One encoding per text | Yes | Yes |
| No 00 byte | Except for U+0000 | Yes, U+0000 included |
| Line feed, tab, carriage return and space bytes never part of another character | Yes: every byte below 80 is an ASCII character, and the bytes of other characters are all 80 or above ([RFC 3629 §3](https://www.rfc-editor.org/rfc/rfc3629#section-3)) | Yes: 03 is always a line feed, 02 a tab, 05 a carriage return and 07 a space ([§13.5](../reference/specification.md#135-no-byte-below-08-inside-a-code-point)) |
| Standard | Unicode standard | Steno Encoding, version 1, an open specification, free to implement |
| Implementations | Every platform | Reference implementations in C, .NET, Go, Java, Python, Rust and TypeScript |

## What It Means for a Store

These follow from the measured sizes; none of them was measured in a database.

- **More values per page (calculated).** On 16-character values, 507 Cyrillic values fit in 8 KB in Steno against 299 in UTF-8, 513 against 201 in the Indic scripts, and 387 against 206 in Japanese. In Latin script it is 544 against 522.
- **Less to read and to cache.** A store that keeps fewer bytes reads fewer pages from storage for the same values, and holds more of them in the same cache.
- **Smaller index keys.** An index on a text column stores the bytes of each key, so its pages hold more keys as well.
- **Transcoding only at the edges.** A store that compares, sorts and matches the bytes pays the transcoding cost when text enters or leaves it, not on every comparison.

## Choosing

- **Choose Steno when** a database or key-value store keeps the text as values or keys and works on them as bytes, above all for text outside Latin script.
- **Choose UTF-8 when** the text is exchanged with other systems, or when the text is mostly ASCII and the time to transcode matters more than its size.
